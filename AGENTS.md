# AGENTS.md — AI Agent Guide for harness-wiki

> Instructions for AI coding agents working on this codebase.

## Project Identity

- **What:** an HTTP server for **LLM-maintained wikis** — persistent, interlinked markdown knowledge bases that a model builds and keeps current from the sources you ingest (Karpathy's "LLM Wiki" pattern). Built on the [harness](https://github.com/gurcuff91/harness) SDK, so any provider harness supports works.
- **Language:** Go 1.25+
- **Module:** `github.com/gurcuff91/harness-wiki`
- **Binary:** single binary, entry point in `cmd/harness-wiki/main.go`
- **Version:** single source of truth in `internal/version` (`version.Version`), injected via ldflags from the `Makefile` (`VERSION=`); falls back to `"dev"` for a plain `go build`.
- **Dependencies:** `github.com/gurcuff91/harness` (the SDK) and `github.com/google/uuid`. Nothing else is direct. No new dependency without the owner's approval.

## The one thing to understand first

**Two "AGENTS.md" files exist, and they are not the same thing.**

1. **This file** — the guide for a coding agent working on *this repository*.
2. **`harness-wiki/<slug>/AGENTS.md`** — one per wiki, written by the maintainer at init time: **the wiki's own schema** (how its pages are organised, what to do on each operation). The maintainer sub-agent reads it because the wiki's folder is its working directory. It is generated, not hand-maintained, and it is data — never edit it from here.

The wiki's folder layout, and what each part is:

```
harness-wiki/<slug>/
  wiki.json     manifest {slug, description, created_at} — the only source of truth
  AGENTS.md     the wiki's schema (generated by the maintainer)
  raw/          immutable sources, copied in at ingest
  wiki/         the pages (index.md and log.md are maintained by the maintainer)
  .lock         present only while an operation runs
  .pending      present only if an ingest or lint did not finish cleanly
```

## Architecture

The layers, bottom to top. **Each package only knows the one below it** — there are no cycles, and adding one means a rule is in the wrong place.

```
cmd/harness-wiki   ← the binary: flags, the server, the signal handling
api/               ← HTTP surface: six REST endpoints + the MCP endpoint + the OpenAPI document
mcpserver/         ← the same operations as MCP tools, over Streamable HTTP
service/           ← the RULES of an operation: the lock, the pending marker, the timeouts
maintainer/        ← the AI side: a harness sub-agent whose cwd is the wiki's folder
wiki/              ← persistence: folders, the manifest, the lock, the pending marker (pure, no model)
client/            ← the typed Go client for harness-wiki's own REST API
```

- **`wiki/`** is pure persistence: it **never invokes a model**. It imports nothing from `agent/`, `server` or `internal/providers`, and is part of the SDK — an SDK consumer can implement `Store` for another backend or open the default filesystem one with `OpenFS`.
- **`maintainer/`** is the only package that talks to a model. It builds a harness sub-agent with `agent.New`, `agent/resources`, `agent/store` and `agent/tools`, and gives it the wiki's folder as its working directory so it reads **that wiki's** `AGENTS.md` as project context.
- **`service/`** holds the rules the HTTP layer must not re-invent: which operations take the lock, which run in the background, when the `.pending` marker is kept, what is reported when something is cut short.
- **`api/`** only translates: a request body becomes a service call, and the service's typed errors become status codes. **The status code comes from what the error IS** (the `wiki` package's typed errors), never from its wording.
- **`mcpserver/`** is a thin protocol layer over the same `service`, so the rules of every operation are the same and are not repeated there.

### The two HTTP surfaces

**REST** (`api/`), standard library `ServeMux` with Go 1.22 patterns — no router dependency for six routes:

```
GET    /api/wiki                  list every wiki with its live status
POST   /api/wiki                  create a wiki                              → 201
DELETE /api/wiki/{slug}           delete a wiki
POST   /api/wiki/{slug}/ingest    ingest sources, in the background           → 202
POST   /api/wiki/{slug}/lint      health-check and repair, in the background  → 202
POST   /api/wiki/{slug}/query     ask a question, synchronously (no lock)     → 200
GET    /api/docs                  the Scalar API reference UI
GET    /api/docs/openapi.json     the OpenAPI document
GET    /api/server                liveness
```

**MCP** (`POST /mcp`): Streamable HTTP, **stateless** — no `Mcp-Session-Id`, no SSE, POST only (GET/DELETE → 405 + `Allow`). Six tools (`WikiList`, `WikiCreate`, `WikiDelete`, `WikiIngest`, `WikiQuery`, `WikiLint`) that are thin adapters over the same `service`. A tool error is a result with `isError: true`, not a JSON-RPC error.

### The MCP client timeout (the setting users get wrong)

A user points harness at this server like this:

```json
"mcp": { "wiki": { "url": "http://127.0.0.1:8787/mcp" } }
```

harness's MCP client has **two per-server timeouts**, and since **harness v0.102.0** they are:

| Setting | Bounds | Default |
|---|---|---|
| `timeout` | **ONE tool call** | **300000 ms (5 min)** |
| `connection_timeout` | connecting (initialize + tools/list) | 30000 ms (30 s) |

Before 0.102.0 the names were the other way round (`timeout` = connecting, `call_timeout` = the call). There is **no alias**: the old `call_timeout` key is ignored.

**This matters here:** a `WikiQuery` may legitimately run up to **30 minutes** (`service.MaxTimeout`; the tool's own default is 300 s). With harness's 5-minute default, **a query longer than 5 minutes is cut off by the client**. A user who expects the full 30 minutes must raise it on the server's entry:

```json
"mcp": { "wiki": { "url": "http://127.0.0.1:8787/mcp", "timeout": 1800000 } }
```

`timeout` is in **milliseconds**, and it is the *harness client's* limit, not the server's: the server's own cap is `service.MaxTimeout` (30 min) and the tool's parameter `timeout` (seconds, at most 1800).

## Key contracts

- **The lock** (`.lock`) is per wiki and is taken by the operations that mutate it. A **query takes no lock** — it only reads, and must never block on an ingest.
- **`.pending`** is left behind when an ingest or lint did not finish cleanly. Its presence is the wiki's "needs attention" signal, and it is reported in `GET /api/wiki`.
- **An ingest is all-or-nothing**: sources are copied into `raw/` first, and the integration step either completes or leaves the wiki pending.
- **The manifest `wiki.json` is the only source of truth** for a wiki's slug and description — never infer them from the folder name.
- **The service's typed errors are the API's status codes.** A new failure mode needs a typed error in `wiki/` (or `service/`), never a new string match in `api/`.

## Development Workflow

```bash
make build     # build the binary (injects the version)
make test      # go test -race -count=1 ./...
make vet       # gofmt check + go vet
make install   # build + install to ~/go/bin
./harness-wiki serve --port 8787
```

### Releasing

`git push origin main`, then `make release` (tags HEAD, with the CHANGELOG entry as the tag message), then `make release-push` (pushes only the tag; it fires `.github/workflows/release.yml`, which builds the binaries and publishes the GitHub Release). Afterwards, download the published asset and verify it with `shasum -c SHA256SUMS.txt`, then `make install`.

**One version at a time:** bump `VERSION` in the Makefile, write the CHANGELOG entry, tag, push. Several versions accumulated before a single tag leave the release list with a gap (harness did that once: `v0.100.0` → `v0.101.3`, with four unpublished versions in between).

## Testing

- `make test` runs the suite with `-race`. The maintainer tests use **fake LLMs** and a real harness agent over a temp directory — never a live provider.
- The MCP surface is tested through the **real harness SDK client** (`harnessmcp.NewHTTPTransport`/`NewClient`), not a hand-rolled one: that is what proves the two sides agree.
- An end-to-end run needs the **absolute** path of the binary (`/tmp/fake_llms.py`-style harnesses parse it out of the output).

## Conventions and anti-patterns

- ❌ **A model call in `wiki/`** — the store is pure persistence; the AI side is `maintainer/`, one layer above it.
- ❌ **Business rules in `api/` or `mcpserver/`** — both translate; the rule belongs in `service/`.
- ❌ **Matching on an error's wording** to pick a status code — use the typed error.
- ❌ **A router dependency for six routes** — the standard library's `ServeMux` is enough.
- ❌ **A session or SSE in `/mcp`** — the server is stateless on purpose.
- ❌ **Editing a wiki's `AGENTS.md` from this repo** — it belongs to the wiki, and the maintainer owns it.
- **A background job is followed through `GET /api/wiki`**, not through a job id or a websocket.
